# Worker 编排

本 Skill 只规定主 Agent 的委派、拆分、路由和验收策略。底层进程、模型发现、并发、取消和路径校验由 `worker` Extension 负责。

## 主 Agent 自己完成

以下工作通常直接完成，不值得委派：

- 纯解释类问题；
- 只需读取少量代码；
- 极少量且位置完全明确的修改；
- 委派成本高于直接完成；
- 高度依赖用户连续反馈；
- 细粒度视觉试调；
- 需要持续和用户实时协商。

## 自主委派

以下工作适合 Worker：

- 边界清晰的实现或明确 Bug 修复；
- 大量代码搜索、调用链调查；
- 测试编写或执行；
- 独立 Review；
- 可以独立验收的子任务；
- 能降低主会话上下文压力的工作；
- 可以安全并行的独立模块。

边界清晰且可独立验收时自主调用，不先询问用户。主 Agent 始终负责最终 diff、验证和交付。

## 先调查再实施

需求有不确定性，但代码事实能够消除歧义时，先调用 `scout` Worker。事实未确认前不要直接实施。调查结果应压缩为调用链、根因、证据和建议边界。

## 任务契约

每次委派尽量提供：

```yaml
mode:
objective:
context:
relevantFiles:
allowedPaths:
forbiddenPaths:
acceptanceCriteria:
verificationCommands:
outputRequirements:
```

不要只发送“帮我把这个功能做好”。`relevantFiles` 只是读取提示，可包含绝对路径、`cwd` 外路径或 glob，不授予写权限。写入模式必须给出非空 `allowedPaths`；`allowedPaths` 和 `forbiddenPaths` 必须是 `cwd` 下的相对路径或 glob，敏感目录应加入 `forbiddenPaths`。验收条件应可通过 diff、编译、测试或明确代码证据判断。

## 并行原则

只有真正独立的任务才并行。批量调度不会因存在任意写任务就把整批降为串行，而是在 `maxConcurrentWorkers` 内逐项检查冲突并保留输入结果顺序；队首任务被正在运行的任务阻塞时，可以扫描并启动后续可证明独立的任务。单项失败不取消兄弟任务。

适合并行：

- 不同服务的只读调查；
- 不同模块且全部 `allowedPaths` 明确为不同兄弟文件或目录子树；
- 写入范围独立的测试与文档；
- 多个互不依赖的分析方向。

不适合并行：

- 只读任务与任意写任务（只读任务没有完整声明读取集）；
- 修改同一路径、路径节点存在祖先/后代关系，或显式目录子树重叠；
- glob 的静态目录前缀重叠，或使用根级、无法静态解析的 glob；
- 不同 `task.cwd` 解析到主工作区后重叠，符号链接规范化后指向同一范围，或遇到悬空符号链接；
- 共享接口仍未确定，或后一个任务依赖前一个结果；
- 多个 Worker 需要持续协商；
- 共同修改生成文件或锁文件。

冲突判定只使用 `task.cwd` 与全部 `allowedPaths`，并采取“无法证明独立即冲突”的保守规则；`forbiddenPaths` 不用于缩小声明写范围。无 glob 的路径即使当前是目录也只表示精确路径；声明目录后代必须使用 `dir/**`，与写入 guard 的匹配语义一致。写入路径可能重叠时改为顺序执行，或由主 Agent 明确创建独立 Git worktree。只有与兄弟写任务真实重叠的任务才会将 `changed_files` 限制到其规范化声明范围；串行任务保留完整原始 delta。结果中的 `observed_changed_files` 始终保留 Git 快照观察到的完整路径，且 `risks` 会说明共享 worktree 下范围外变化的来源无法确定。主 Agent 仍须检查整批实际 diff。不要让 Worker 自行创建 Worker。

## 后台问答与回收

主 Agent 只使用 **`worker` 一个工具**。每个会话同一时刻只允许一个未完成批次；并行任务必须放在**同一次 `worker({ tasks: [...] })`**，不得在同一轮使用多个独立 `worker({ task })` 调用（包括 `Promise.all`），否则第二次启动会立即返回 `status: "blocked"`、`error: "active_batch"` 和 `activeBatchId`，不会等待或取消已有任务。用该 ID 回答、续等或取消；批次结束且清理完成后才能启动下一批。`worker({ task })` 或 `worker({ tasks })` 启动批次后，持续等待到出现 `ask_parent` 问题或整批完成；没有 30 秒轮询返回。提问时立即返回，其他独立任务继续在后台运行。返回的 `batchId`、`tasks[].taskId`、`questions[].id`（作为 `answers[].questionId`）是后续操作的准确标识，不要从预览正文推断标识。

1. 检查 `finished` 与 `questions`；出现问题而返回不等于批次结束。
2. 调用 `worker({ batchId, answers: [{ taskId, questionId, answer }, ...] })` 批量提交当前能回答的问题，工具会继续等待下一次提问或整批完成。整组回答先全量校验再应用；未知、跨任务/批次、重复、已取消或过期的 ID 明确报错，任何一项无效均不会部分提交。可只答部分问题；仍有待答问题时立即返回。回答不改变任务原有路径权限；需要扩展边界时先取消、回收，再建新任务。
3. 调用 `worker({ batchId })` 继续等待已有批次，不创建新批次；已有待答问题会立即返回，不要绕过问题反复续等。没有问题时持续等待到整批结束或新问题。可附加 `questionOffset` 选择下一次响应的历史页（每页 8 条）；不提供轮询超时、只查询或列出批次模式。
4. 不再需要的任务用 `worker({ batchId, cancel: true })` 取消；该调用等待进程清理和锁释放，返回 `finished: true` 后才能安全访问其写路径。取消已结束批次是幂等操作。一个任务提问或失败不取消其他任务。
5. 所有正在执行的启动、续等、回答调用被中断时，都会取消其批次并等待清理；调用已返回后再中断旧调用不影响后台批次。已中断的启动不创建任务；已中断的续等/回答取消已有批次且不应用答案。取消模式不能被中断成未完成清理的提前返回。
6. 启动字段 `task/tasks/manual` 不能与 `batchId/answers/cancel/questionOffset` 混用；`task` 与 `tasks` 二选一；`cancel` 只能为 `true` 且不能与 `answers/questionOffset` 混用；`answers` 必须非空。无效输入不改变批次状态。
7. 主 Agent 在交付前必须回收或取消所有后台批次。后台不会自动向主 Agent 的忙碌消息队列注入续跑消息；必须主动再次调用 `worker`，避免等待消息队列导致死锁。

等待回答的 Worker **继续占用并发槽和路径锁**。并发限制和冲突队列在当前批次内生效；已有未完成批次时不允许新开第二批次，即使第一个调用仍在等待且尚未提问。不要要求被锁阻塞的任务先产出才能回答，应该直接决策、取消或重新拆分。运行期间配置下调并发不会杀死已有任务。主 Agent 自己的工具不受 Worker 调度锁拦截，不要同时改动它们的路径。

TUI 每批次只有原始 `worker` 卡片，调用返回后仍动态刷新状态、待答问题和最近两条回复；Pi 的展开操作在同一卡片显示完整问答。续等、回答、取消调用仍由**真实主 Agent** 发出并进入模型历史，但后续卡片完全零行，不使用内部/fork 协调模型。合法批次的控制错误显示在原卡片且仍作为工具错误返回；未知批次或无法归属的错误保留独立可见输出。正文预览可截短，路由 ID 不变。重载、切换、树导航、退出会取消清理，不恢复后台进程；仅当前分支的最新持久化快照按原始调用 ID 合并到原卡片，历史计时冻结，不串入其他分支或批次。提问默认等待 120 秒，可设 1–600 秒，通常仍计入任务总超时；每任务最多 32 问、每问 2000 字符、每答 4000 字符、当前会话最多 64 批次。

### 需要用户确认时

主 Agent 先判断能否在既定权限内自行答复；需要用户选择或确认才调用 `ask_question`（单题/多题均可）。实际交互开始前会等待暂停确认：只暂停当前等待 `ask_parent` 的任务总预算及两端问题预算，新到的问题也加入；独立任务和可执行的排队任务继续，等待者仍占槽和锁。受管子进程的总截止时间由 Runtime 统一控制，结束交互后恢复**剩余**预算。它不冻结任意运行工具，也不暂停终止、清理、Git 或 UI 计时。

人工等待最多 **30 分钟**；同一问题从首次暂停起也受上限约束，嵌套或并发确认不能无限续期，到期取消受影响任务并清理。Esc、signal、异常、会话结束均解除暂停；无 UI/RPC 不打开自定义问卷且不产生答案。取消确认绝不是默认同意，多题未提交草稿也不构成授权。用户结果只返回真实主 Agent，主 Agent 必须检查并使用原问题 ID 显式提交 `worker({ batchId, answers: [...] })`，不能声称系统已自动传给 Worker。结束确认后不要拖延到普通剩余预算过期。

任何回复都不能扩大 allowedPaths/forbiddenPaths 或其他任务权限；扩权限必须先 `cancel` 并等待回收，再建新任务。涉及全局危险操作或要求所有相关写入停止的决策，应**先取消相关批次，再问用户**，不能把预算暂停描述为所有运行工具都已安全停止。

## 路由

### Fast

用于目标明确、范围小、失败易检测且成本低的局部工作，例如查找符号、短调用链、CSS/文案、明确类型错误、已有测试、机械修改、简单测试，以及功能实现完成后由主 Agent 自动追加的常规 Review。

### Normal

日常默认。用于普通功能、常规 Bug、多相关文件、API、前后端功能、普通重构、单元或集成测试、中等调用链和普通 Review。不确定 Fast 或 Deep 时选 Normal。

### Deep

用于困难任务，例如跨模块/服务/语言、根因不明、并发与异步状态、缓存一致性、重试容错、资源生命周期、数据同步、复杂架构、大范围回归、重要 Review、约束很多或 Normal 已失败的任务。Deep 是自动路由的最高任务复杂度级别，文件多本身不等于困难任务。

### Max

`Max` 不是任务复杂度级别，仅代表用户显式要求的最高执行强度。仅当用户主动明确要求 `Max`、最高强度或同等表述时使用，并设置 `userExplicitMax: true`。Max 不参与自动路由，也不得静默降级。各档位的模型与 thinking 仅由 `worker-settings.json` 配置。

## Review 与返工

- 小任务：Worker → 主 Agent 验收。
- 普通任务：Worker → 主 Agent 验收。
- 困难任务：实现 Worker → 独立 Deep Review Worker → Fix Worker → 主 Agent 验收。

功能实现完成后，如果 Review 是主 Agent 自动追加而非用户明确要求，默认使用 `preset: fast`；具体模型和 thinking 读取 `worker-settings.json`。不得为这种常规自动 Review 使用 Max。困难任务需要加强审查时使用 Deep；只有用户主动明确要求最高执行强度时才可使用 Max。

不要让所有小任务默认走完整 Review 流程。Review finding 必须有文件、位置、证据、影响、建议和置信度；只修复主 Agent 已确认的问题。

## 主 Agent 验收

Worker 声称完成不代表任务完成。主 Agent 至少检查：

1. 实际 Git diff 与修改范围；
2. 用户原有未提交修改是否被保留；
3. 测试和验证命令是否真实执行；
4. 每条验收条件是否有证据；
5. 是否有 blocker、越界写入、模型降级或未解析输出；
6. 是否需要定向返工或独立 Review。

批量结果彼此独立；一个失败不得掩盖其他任务。任何 `blocked`、`failed`、Max 降级、越界文件或实际模型不匹配都不能直接验收为成功。
