# 设计澄清

仅用于本次设计讨论，不进入编码。目标是对齐当前 MVP，而非穷尽未来需求。

1. **先查事实**：阅读相关代码和现有文档，能查到的事实自行核实。指出实现与描述的矛盾，区分事实、假设和待决策项。
2. **分轮提问**：使用 `ask_question`，每题给出清晰选项并标注推荐方案与简短理由。同轮合并可独立决定的问题；依赖未决答案的问题留到下一轮。只问影响当前范围、行为、约束或验收的关键问题，不反复确认已定事项。
3. **检验共识**：澄清模糊术语，用少量具体场景检验边界与失败行为。优先复用项目已有概念和模式，不引入无必要的功能、抽象或文档。
4. **按需落盘**：默认只在对话中总结，不创建或修改文件。用户要求落盘时优先更新现有文档；术语定义才放入 `GLOSSARY.md`。仅对难以逆转、脱离背景难理解且存在真实取舍的决定提议 ADR，经确认后再写入 `docs/adr/`。
5. **确认后结束**：关键问题解决后给出短摘要：目标与范围、已定行为和约束、验收方式、不做事项及剩余不确定性。用 `ask_question` 确认理解一致或指出需调整项，然后结束本流程；后续实现需另行授权。
