# Worker background Q&A

## Protocol and ownership

The parent registers **only `worker`**. Its four modes are:

```js
worker({ task: { mode: "scout", objective: "Trace the call chain" } }) // or tasks: [...]
worker({ batchId: "<returned batchId>" })
worker({ batchId: "<returned batchId>", answers: [
  { taskId: "<tasks[].taskId>", questionId: "<questions[].id>", answer: "Use option A" },
] })
worker({ batchId: "<returned batchId>", cancel: true })
```

- Only **one unfinished batch per session** is permitted. Put parallel work in a single `tasks` array; do not issue independent `worker({task})` starts in the same tool-call round (including `Promise.all`). A second start returns `status: "blocked"`, `error: "active_batch"` and `activeBatchId` immediately, even if the first invocation has not yet produced a question; it never waits for a concurrency slot or cancels the first batch. Answer, continue or cancel using that ID; a new start is allowed after the first batch finishes and cleanup completes.
- Start requires exactly one of `task`/`tasks` (1–12 tasks); `manual` is optional and start-only. Continuation requires `batchId`; it never creates another batch or reloads routing settings. Start fields cannot be mixed with continuation fields. `cancel` must be `true` and cannot be mixed with `answers` or `questionOffset`. Unknown fields, empty answers arrays and malformed inputs are rejected before any work is admitted.
- Start, continue and answer calls wait **until a pending question or whole-batch completion**, with no 30-second polling return. A question returns immediately (including a previously returned question); independent tasks keep running. Answering validates the entire array before applying anything, then waits for the next question or completion. Partial submissions are allowed: remaining questions return immediately. Unknown, foreign, duplicate, cancelled and expired IDs are rejected; an invalid answer never partially applies other answers. Use the exact returned routing IDs, not preview text.
- Responses contain `batchId`, `tasks[].taskId`, `questions[].id` and `finished`. Existing compressed single/batch results are under `result`; control IDs are never removed by result compression. Optional `questionOffset` on continue/answer selects a history page (8 records) in the next response; it does not enable polling. There is no list/status-only mode or `waitMs`.
- Child `ask_parent({ question, timeoutMs? })` is unchanged and runs through the explicitly loaded `ask-parent.ts` extension. It sends UUID-tagged JSON frames on an inherited **duplex fd 3**, not stdout, stdin, a shared file, an HTTP server or Pi's model-message queue. Its promise resolves only with the matching answer.
- Cancel aborts pending/running tasks and removes queued tasks, then waits for cleanup and returns `finished: true`. Paths remain locked until cleanup completes; cancellation of an already-finished batch is harmless. **Aborting any active start/continue/answer invocation has the same cancel-and-clean-up semantics.** A pre-aborted start admits no work; a pre-aborted continuation cancels the existing batch without applying answers. Invalid inputs fail without changing the batch. After a call returns, its signal is detached: later aborts do not affect background tasks. Cancelling a cancel invocation does not interrupt cleanup.

`runtime.ts` retains its conflict queue across batches, but the tool layer admits only one unfinished batch at a time. Within that batch, waiting tasks keep both their slot and their path locks through process termination and result validation. Independent tasks still run; conflicts preserve queue order. A lower concurrency setting affects admission, not already-running processes.

`process.ts` retains route selection, Git delta attribution, event-stream parsing and usage accounting. IPC closes on exit/cancel/timeout; process groups are terminated and escalated to SIGKILL. Shutdown timers capture their original children so they cannot kill a replacement session's workers. Session shutdown/replacement, reload and tree navigation cancel the runtime. The process exit hook force-kills tracked children.

## TUI

The **original `worker` tool result card** is the only card for a batch and stays live after the invocation returns. Follow-up wait/answer/cancel calls still execute on the **real main Agent** and remain in the model transcript, but render zero lines (including partial arguments, expansion and redraw). There is no hidden/forked coordinator model. `renderShell: "self"` plus an actual empty Component suppress the whole follow-up container; empty `Text` would leave Pi framing behind. Unknown/unattributable errors remain visible. Errors attributable to a live batch are shown on its original card and still throw a genuine model-facing tool error. Its batch identity, completion count, task phases, waiting questions and two recent replies update in place; there is no separate command, widget, footer or overlay. Use Pi's normal tool expansion to read the complete question/answer history in that same card. Collapsed previews shorten question/answer bodies only; routing IDs remain unchanged. Text is sanitized, wrapped and width-bounded, including on narrow terminals.

`renderResult` resolves `batchId` against its session-owned runtime. On reload/tree navigation a `getBranch()`-only index merges the latest snapshot into its `originToolCallId` card. Revision-tagged custom entries persist question transitions, task completion and control errors even after the original invocation returns; tool-result details also participate in reconstruction. Different batches and abandoned branches cannot borrow each other's origin. History is immutable presentation, never a recovered runtime. The installed Pi `ToolRenderContext` exposes **`invalidate()`**, not `requestRender()`: Pi's `ToolExecutionComponent.getRenderContext()` implements it by rebuilding that row and calling `ui.requestRender()`, even for a final result. No post-return `onUpdate` is used. A session-owned refresh coordinator coalesces live changes (50ms) and advances elapsed time (1s). It starts only for rendered active batches and clears periodic timers on completion. At most one original-row callback per live-session batch is retained for later control errors (64 batches maximum); all callbacks/timers are released at session cleanup. There is no reliance on an undocumented tool-component disposal hook. Row-local ownership prevents old components from attaching to a replacement runtime. Pi reload and session/fork rebind can render historical rows before the first `session_start`; those startup rows retain their initial owner, then receive the selected branch's snapshots and one invalidation when binding finishes. Only this initial owner is hydrated: subsequent session replacement still freezes old rows. Startup callbacks are released after binding or shutdown. Theme and expansion changes rebuild the card normally.

## Human confirmation (bounded pause)

The main Agent answers Workers itself. If user judgment is required, it calls `ask_question` and then explicitly submits its decision with `worker({batchId, answers: [...]})`. The user's raw answer is **never automatically forwarded**. Esc, cancellation, missing UI, RPC, exceptions, abort and session shutdown are not approval. Cancelled questionnaires discard unsubmitted draft answers.

- Single questions and questionnaires use `shared/interaction-lifecycle.ts`: synchronous events carry `waitUntil` acknowledgements; the custom UI opens only after pause preparation. Token-based begin/end is idempotent and supports overlapping interaction sources. `ask_question` itself uses a cancellable FIFO because Pi's non-overlay custom UI replaces the editor: concurrent SDK/tool calls never open two questionnaires at once. Prefer merging related questions into one `questions` array. Queued calls acquire no pause token; their queue time counts toward the same 30-minute interaction cap, which is not reset when they reach the front. Aborted/expired queued calls never open a UI, and session shutdown/start/tree cancels both the active questionnaire and all queued calls. All exits run `finally` cleanup. RPC/non-TUI returns unanswered details without opening an interaction (no custom terminal UI fallback is claimed).
- Only tasks currently in `ask_parent` are paused. Questions arriving while the interaction is open join automatically; independent tasks and eligible queue entries continue. Waiting tasks **retain their slot and path locks**. This is a budget pause, not OS suspension of arbitrary running tools.
- Four deadline sites are covered: runtime total-task active budget, parent question timer and `expiresAt` validation, child question timer, and process deadline. Managed `executeTask` explicitly delegates its total deadline to the runtime; standalone `runPiWorker`/`executeTask` retain their own process timeout by default. Question-specific fd3 pause/resume frames carry validated tokens and bounded deadlines, and require child acknowledgements (3-second control timeout fails closed). Resume restores remaining time, not the full original allowance. `pausedUntil` identifies a paused question; its ordinary `expiresAt` is recomputed on resume.
- **30 minutes maximum per human interaction**, also bounded from a question's first pause so nested/new tokens cannot extend a pending question indefinitely. Reaching the bound cancels the affected waiting task, closes its question and initiates normal process cleanup. Late replies/resumes cannot revive it. Bulk reply validation checks the task's running/non-aborted state and total remaining budget as well as every question budget before applying any answer. Task completion also checks the total budget before accepting success, even when the clock has passed the deadline but its timer callback has not run. Kill escalation, IPC-control, Git, UI-refresh and cleanup timers are never paused.
- A cancelled confirmation does not mean consent: the main Agent must decide whether to clarify again or cancel the batch. Changing write permissions requires **cancel → await cleanup → new task contract**. For global dangerous decisions, cancel relevant batches *before* asking; do not claim that running tools have been paused. No lifecycle event changes allowed/forbidden paths or grants new privileges.

## Limits

- Default answer timeout: 120 seconds; tool range: 1–600 seconds. The overall task timeout remains effective while waiting for the main Agent, except for the bounded actual human interaction above. There is no slot donation/resumption scheduler.
- Up to 32 questions/task, 2000 characters/question, 4000 characters/answer, 64 retained batches/session; history pages contain 8 records. Result compression applies to `result`; bounded IDs/questions/history are a separate control envelope.
- No automatic follow-up/steering message is injected. The parent must actively reply/wait and collect or cancel unfinished batches before final delivery.
- Answers cannot change the original write contract. Scheduler locks coordinate Workers only, not the main Agent's own tools, external processes, other Pi sessions or other worktrees.
- Live processes never resume after reload/session switch/tree navigation. Historical original cards use the latest persisted snapshot on the selected branch, are labelled as snapshots and freeze elapsed time; old in-memory rows freeze their last state. Shutdown does not append old runtime data into a newly selected branch. An interrupted session can therefore retain a historical waiting/running label, not a live task. Use `questionOffset` pagination for model-facing history.
- Tested on Linux/Node 22.19. Windows process-tree cleanup and actual terminal keyboard interaction need platform smoke testing. Automated tests use model-free subprocess fixtures; no paid model was invoked.


Tests cover synchronous single-active-batch admission (concurrent/sequential starts, no-question waits, cleanup and restart), strict single-tool mode/input validation, atomic bulk answers and multi-round questions, no-question waits beyond 30 seconds (virtual time), cancel/abort cleanup on initial and continuation calls, and the real fd3 transport and registered child tool, fragmented Unicode, concurrent questions, out-of-order answers, stale replies, timeouts, cancellation, retained locks/slots, cross-batch scheduling, independent completion, forced shutdown, replacement-session safety, original result compression/usage/attribution, original-card refresh after return/reply/completion (using the installed Pi tool-execution component), expansion, session cleanup, timer release, immutable history snapshots and narrow-width rendering. Additional coverage uses the installed Pi self-shell component to assert truly zero-line follow-ups, branch-specific reload reconstruction and original-card control errors. Virtual-time and real-fd3 subprocess tests cover remaining-budget pause/resume at all four deadline sites, nested/late tokens, missing acknowledgements, the hard human limit, independent work and lock retention, plus single/multi-question UI submission/abort/Esc/exception/non-TUI/shutdown paths. Lifecycle regressions additionally render a real Pi tool row before `session_start`, exercise installed `renderBeforeBind` ordering and fork isolation, drive concurrent questionnaires through installed `InteractiveMode.showExtensionCustom` (one editor owner), and advance mock Date without dispatching timers to reject late atomic replies and late successful task completion. These are model-free tests; a real terminal keyboard smoke test is still recommended.
